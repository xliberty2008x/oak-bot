# Browser agent implementations for Oak's dynamic login flow

Research date: 2026-10-11 UTC. Read-only inspection of official documentation, package registries and pinned upstream source. No upstream code was installed or executed; no provider/account/browser session was opened. Source checkouts were retained outside Oak Git. Source findings are stronger than marketing claims, but are not an acceptance test of Google, Instagram or TikTok.

## Decision-relevant result

The reusable implementation is a **browser observation/action harness driven by Oak's existing Codex model**, with Oak retaining the private credential channel and the human form renderer. Browser Use already implements a full repeated-observation agent; Stagehand v4 deliberately leaves that loop to the caller; Skyvern combines a full agent with workflow and credential infrastructure. None of the inspected contracts is a drop-in webpage-to-private-human-login-form renderer that establishes successful Google/TikTok login on this host.

For an evaluation shortlist: Stagehand's current local facade and Browser Use's direct local MCP/DOM layer are plausible harness candidates. Browser Use's full Agent is a useful loop reference. Skyvern provides unusually concrete credential-pause, OTP and reference-validity examples, but replacing Oak with its whole stack would introduce a second orchestration/service/model system and a different license. These are engineering judgments from the source below, not measured reliability rankings.

The crucial distinction is between (a) asking a model to reason from a new page observation after each transition, (b) safely executing an action on that page, and (c) reconstructing an appropriate human-facing form while keeping entered values out of the model. Browser automation SDKs solve substantial parts of (a)/(b). They do not automatically establish (c).

## Browser Use: a real repeated-observation agent, plus a usable lower layer

**Actual loop.** `Agent.step()` prepares current browser state, asks the LLM for structured next actions, executes them and records results. `_prepare_context()` refreshes browser state and page-specific action models before the model call; `run()` repeats the step. Batch execution stops after declared page-changing actions or a URL/focused-tab transition. This is different from parsing a login form once and hoping its selectors remain valid. Sources: [agent/service.py, step/context](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/browser_use/agent/service.py#L1035-L1210), [batch guards](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/browser_use/agent/service.py#L2740-L2850).

**Page representation and references.** `DomService` combines CDP accessibility, DOM and DOMSnapshot information. The serializer assigns actionable indices from backend DOM node IDs, with collision handling and per-session identity; it marks newly appearing nodes against the previous snapshot. These are current browser-node references, not permanent provider IDs. Navigation or replacement requires fresh observation; the batch guards alone do not establish that an unchanged-URL SPA has preserved a particular login form. Sources: [dom/service.py](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/browser_use/dom/service.py#L379), [serializer.py](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/browser_use/dom/serializer/serializer.py#L637-L766).

**Human steps.** Public `pause()/resume()` and step callbacks keep the loop externally controllable. Custom tools can request human information. The generic human-help example returns the answer as tool content, which would expose a password to the model if reused literally. Oak should instead pause for an opaque credential request and return only completion/next-state information. Sources: [pause/resume implementation](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/browser_use/agent/service.py#L3917-L3937), [custom-tool documentation](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/AGENTS.md).

**Secrets and OTP.** `sensitive_data` supports domain-scoped aliases; replacement occurs in the action registry after model generation. A placeholder ending in `bu_2fa_code` generates a current TOTP locally from the seed. Legacy flat aliases are intentionally available on all domains. The agent warns when secrets are supplied without a matching domain allowlist. This is useful substitution, not a sandbox. Sources: [replacement and TOTP](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/browser_use/tools/registry/service.py#L427-L514), [domain warnings](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/browser_use/agent/service.py#L533-L580).

**What still leaks.** Message filtering replaces known literal secret strings in text parts; image parts are not processed by that filter. Context preparation requests a screenshot even when `use_vision=False` (the source comment mentions cloud sync). Therefore disabling model vision is not equivalent to disabling screenshot capture or retention. Page echo, transformed/split values, browser state and independent diagnostics require separate controls. The direct MCP `browser_type` takes raw text and uses only a heuristic to suppress some echoes; it is not the Agent's private placeholder channel. Sources: [text-only filtering](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/browser_use/agent/message_manager/service.py#L576-L609), [screenshot request](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/browser_use/agent/service.py#L1090-L1104), [MCP typing](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/browser_use/mcp/server.py#L844-L890).

**Fit with Oak.** The full Agent expects a `BaseChatModel.ainvoke()` implementation and normally uses its own model client; Oak's app-server RPC is not that interface. A custom adapter is possible engineering work, not verified built-in ChatGPT-subscription support. Alternatively, use only direct local MCP operations (`browser_get_state`, click/type/navigation), or the CDP/DOM/Actor modules, and let Oak's current model remain the planner. Agent-retry and LLM extraction tools must be excluded unless separately integrated: they instantiate or require another model client. Sources: [model protocol](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/browser_use/llm/base.py#L33-L59), [direct versus agent MCP dispatch](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/browser_use/mcp/server.py#L500-L580), [LLM extraction gate](https://github.com/browser-use/browser-use/blob/c75e8476e26d18b7617643bc2ae082fae8eae431/browser_use/mcp/server.py#L997-L1008).

Browser Harness is another, separate local option: helpers expose CDP, JavaScript, typing, screenshots and HTTP through stdio MCP. It is deliberately a broad coding-agent harness, including agent-written helpers, rather than a credential-isolated form broker. Do not conflate it with the Agent's DOM serializer or `sensitive_data` contract. Sources: [harness architecture](https://github.com/browser-use/browser-harness/blob/dbf0e4f3a37ebc31aaeaf9d378ab1760b5776c15/README.md), [MCP tool surface](https://github.com/browser-use/browser-harness/blob/dbf0e4f3a37ebc31aaeaf9d378ab1760b5776c15/docs/MCP.md).

## Stagehand: current v4 is a harness, not the old autonomous Agent

**Version trap.** v4 removed `agent()`; the caller now supplies code or a tool-calling loop. The official docs explicitly recommend observing after a change and caution against retrying an uncertain action. Older `agent.execute()` examples describe v3 and should not drive a new v4 implementation. Source: [v3→v4 migration](https://docs.stagehand.dev/v4/migrations/v3).

**Actual observation/action path.** `observeService.observe()` captures an accessibility snapshot, sends its tree to inference, and maps returned element IDs to XPath-backed `Action` objects. `act(Action)` can execute that structured action without another inference call; `act(instruction)`/`observe(instruction)`/`extract()` use a model. For Oak's existing model, the lower `page.snapshot()` and deterministic interaction methods are the relevant primitives. Sources: [observeService.ts](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/extension/services/observeService.ts#L91-L156), [actService.ts](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/extension/services/actService.ts#L332-L388).

**References and same-page transitions.** The facade stores a snapshot's per-page XPath map and URL, rejects absent/unknown IDs and a changed URL, and never retries a partially executed action batch. Its documented contract says IDs belong to the latest snapshot. The shown `runActionsNow()` URL guard does not itself prove that the same XPath still denotes the same control after a same-URL DOM replacement. A private human form needs stronger document/form revision binding and revalidation before filling/submitting. Sources: [facade contract](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/integrations/core/src/facade/contract.ts#L162-L227), [snapshot/actions implementation](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/integrations/core/src/facade/tools.ts#L241-L312).

**Human input and login.** The approval cookbook demonstrates pausing an outer model loop, displaying pending values, adding an approval response and resuming; it checks the form did not change before submission. It is an ordinary order-form example using external model/browser keys, not a secret-login frontend. The login cookbook has explicit username/password/submit steps and session persistence; it does not dynamically reconstruct every possible OTP/QR/account-selection step. Sources: [approval implementation](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/examples/cookbooks/approve-form-submission/typescript/src/index.ts), [persisted login](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/examples/cookbooks/persisted-login/typescript/src/index.ts).

**Secret handling.** Prompt construction exposes variable names/descriptions, while `actService` substitutes `%name%` just before interaction and retains placeholder arguments in its successful result. Good reusable mechanism, but the browser's accessibility nodes still carry their `value`, and arbitrary JavaScript, input-value reads, cookies or screenshots are available elsewhere. Diagnostic redaction is heuristic; the integration README explicitly admits page text/typed values can remain sensitive. Sources: [prompt variable metadata](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/extension/prompt.ts#L15-L29), [substitution](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/extension/services/actService.ts#L508-L519), [AX value capture](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/extension/understudy/a11y/snapshot/a11yTree.ts#L154-L168), [logging](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/integrations/core/src/facade/logging.ts#L1-L29).

**Fit with Oak.** The experimental official Codex integration supports existing `codex login`, a persistent stdio MCP server and local Chrome. This establishes an upstream-supported integration shape, not acceptance on Oak. Reuse the persistent facade/browser layer rather than its example agent runner: the example creates a separate Codex thread/home, can copy file-based auth, and changes approval configuration. Oak should retain its own app-server session, exact model, authorization and isolation. With `STAGEHAND_BROWSER=local`, no Browserbase key and no Stagehand AI calls/model key, primitive browser operations need no new model billing. The broad `run` tool executes model-authored JS and should not be exposed to the credential browser. Sources: [Codex integration source/docs](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/docs/v4/integrations/cli-agents/codex.mdx), [backend/model selection](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/integrations/core/src/facade/config.ts), [auth isolation example](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/integrations/codex-sdk/src/isolation.ts).

**Host caveat.** The SDK accepts an explicit browser executable and searches for Linux Chrome/Chromium, so there is no hardcoded x86-only conclusion from this launcher. Its extension transport and Oak's installed ARM Chromium still require a real local test. The launcher disables Chromium sandbox when `CI` is set, when explicitly requested, or when root; deployment must preserve Oak's non-root sandbox behavior. Source: [localBrowser.ts](https://github.com/browserbase/stagehand/blob/f261c38b4dc50c39485f924e8599c1d3c6e37dc7/packages/sdk-ts/src/browser/localBrowser.ts#L279-L375).

## Skyvern: extensive workflow/login machinery, greater integration cost

**Actual loop and references.** `agent_step()` obtains a new scraped page/prompt (or an explicitly managed speculative snapshot), generates actions, executes them and finalizes/verifies the step. The scraper annotates elements with `unique_id` and retains DOM/frame mappings. The newer direct MCP observer has snapshot generations and document IDs, omitted input values by default, and refusal on stale references. These are useful reference implementations for transition handling. Sources: [agent loop](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/forge/agent.py#L4708-L4960), [DOM identity](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/webeye/scraper/domUtils.js#L2350-L2488), [MCP snapshot currency](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/cli/mcp_tools/browser.py#L4070-L4295).

**Human pause is implemented, but distinguish its products.** `HumanInteractionBlock` pauses a workflow for approve/reject/timeout, with notification/browser-session UI. Copilot credential acquisition separately emits a `credential_required` event and waits on a record bound to organization/chat/turn plus a one-time resume token. Its accounting suspends the model deadline during overlapping human waits. This is much closer to a durable private human-input protocol than a bare Python `input()`, but is a credential-acquisition/build-flow mechanism, not proof of a universal per-page login form renderer. Sources: [HumanInteractionBlock](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/forge/sdk/workflow/models/block.py#L15314-L15565), [credential pause](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/forge/sdk/copilot/credential_pause.py#L1-L24), [deadline accounting](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/forge/sdk/copilot/human_input_wait.py).

**Credentials and OTP.** Workflow context registers opaque secret IDs, resolves their actual values at action execution, and tracks runtime OTPs. Login blocks can use stored profiles/credential bindings. Multi-field OTP handling re-scrapes, reconstructs input groups and compares structural identities after change; old IDs cannot simply be reused after navigation. Code-block credential release also checks the target element's frame/site before releasing a stored credential. These are reusable design lessons, but copying modules requires addressing their dependencies and AGPL license. Sources: [secret registry](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/forge/sdk/workflow/context_manager.py#L1217-L1237), [action substitution](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/webeye/actions/handler.py#L11632-L11670), [OTP rebinding](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/webeye/actions/multi_field_totp.py#L409-L490), [release guard](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/forge/sdk/workflow/models/credential_release.py#L1-L137).

**Secret guarantees are conditional.** The workflow context defaults `mask_secrets=False`; LLM-bound/artifact redaction is gated by workflow Mask Secrets and a global switch. Bare-task artifact rules differ from workflow rules. Visual masking applies CSS to recognized secret/OTP fields, also behind switches. This masks rendering, not the actual DOM value, and does not prove protection against a site's transformed echo or model-accessible JS. `skyvern_observe` omits values by default and never returns password input values, but other tools can read HTML, evaluate code, inspect network or access state. Sources: [redaction gates](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/forge/sdk/workflow/context_manager.py#L2470-L2515), [visual mask gate](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/webeye/actions/handler.py#L589-L623), [CSS mask](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/webeye/utils/page.py#L175-L238), [MCP full surface](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/cli/mcp_tools/README.md).

**Fit with Oak.** The full agent uses LiteLLM/provider clients and service/database/workflow infrastructure. Its hosted MCP supports OAuth as well as keys, but OAuth means signing in to Skyvern's service; it does not make Skyvern's model/browser work part of Oak's ChatGPT subscription. Local direct selectors/CDP operations can be driven by Oak's outer model, but AI-intent actions, extraction, validation and workflow login remain separate inference paths. The direct MCP can therefore be investigated as a subset, not enabled wholesale as a free equivalent of the existing runtime. Sources: [provider factory](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/forge/sdk/api/llm/api_handler_factory.py), [direct versus AI action](https://github.com/Skyvern-AI/skyvern/blob/f5f3f28a9ce0021a1db24286928a7bff6582a1eb/skyvern/cli/mcp_tools/browser.py#L661-L730), [official MCP deployment/authentication](https://www.skyvern.com/docs/developers/getting-started/mcp).

## What to implement/evaluate next, without pretending the browser is a static form

This is an integration recommendation, not an upstream feature claim:

1. Keep the same trusted browser context alive across email → password → method choice → OTP → account selection. Observe again after each actual submit/navigation/DOM replacement; detect meaningful state changes rather than only URL changes.
2. Give Oak's existing model a bounded sanitized observation with visible controls, labels, types, choices, button roles, origin/frame and opaque current references. The model may choose the next interaction and human input schema; broker code validates the schema against the current page. Avoid fixed provider-step regexes as the sole planner.
3. Bind each human form to session, document and form revision. Human values go directly to the broker; the model receives only an opaque completion result. Resolve and revalidate targets immediately before fill/submit. An old form submission must not target a newly replaced control at the same selector.
4. After submitting, observe and classify again: next input, validation error, alternate method, external approval, QR challenge, completion, or unsupported state. QR/push require a dedicated human challenge view/confirmation channel and fresh observation afterward; a generic text field cannot represent them. No inspected source establishes universal QR/TikTok success, and no CAPTCHA/anti-bot bypass is proposed.
5. Preserve uncertainty: if submission may already have occurred, re-observe instead of replaying. Distinguish positive authenticated account evidence from a provider's public page, a user pressing “Done”, or an agent claiming success.

Useful evaluation cases before real accounts: same-URL email→password replacement; password→method chooser; radio/role-button alternatives; six separate OTP boxes; delayed validation/button enablement; rerender between human response and submit; popup/iframe origin transitions; wrong-code retry; QR expiry; cancel/timeout; successful sign-in without a redirect; and credential echoes in labels/text/images. Repeated successful synthetic runs would validate the plumbing, followed by user-authorized provider tests. Upstream benchmark numbers cannot substitute for these tests.

## Oak architecture cross-check

The deployed `e9f5e87` design already re-inspects the page on human polling; it is not literally a one-time HTML parse. However, it **does not run the native model's observe/reason/act loop during login**:

- [login_broker.py:248](../oak/login_broker.py) checks the fixed adapter's `verified()` and returns its `snapshot()` to the human frontend. Submission calls that adapter's `submit()`.
- [login_broker.py:321](../oak/login_broker.py) refuses connected-browser operations until the lease is authenticated/owner-confirmed.
- [login.py:157](../oak/login.py) polls broker status and resolves the original model input waiter only at success or a terminal outcome. Intermediate page state never reaches the model through this path.

Therefore a targeted parser/transition repair can restore supported email→password or method-selection steps without replacing the stack. It should be described as that repair. To fulfill the stronger request that the agent itself observes and rebuilds each step, the protocol must additionally provide bounded, sanitized pre-auth observations and validated pre-auth actions. The model must be allowed to reason between human submissions rather than remaining blocked on one whole-login waiter. Human values must still be consumed only by the broker; returning them through an ordinary model tool response would defeat the existing privacy boundary. This is a protocol/agent-loop change, not something an A2UI renderer or browser-harness installation supplies on its own.

Upstream inspection itself made no production, account or service changes. The accompanying Oak patch and this repository report have a separate validation record.
