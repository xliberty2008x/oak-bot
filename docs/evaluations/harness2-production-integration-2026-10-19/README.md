# Connecting Harness² to the installed Oak

The earlier three-cycle integration required operator CLI work. Merging it
alone would not connect production outcomes to search or start a worker. This
change adds that missing opt-in path, while retaining the rejected procedures
and the original independent quality gates. It is infrastructure integration,
not evidence that Oak's media quality has improved.

## What now runs automatically

The normal managed gateway starts one bounded background worker when
`harness_improvement` is enabled. Actual turn completion, artifact review,
queued/confirmed delivery and owner-reply references create scoped local
metadata cases. Approved supported descriptors reach the existing genuine
Harness² scheduler, fresh-input generation, Propose–Probe–Compose, independent
comparison and admission. The active store is shared with the actual Controller
input path. `/improve status|stop|resume` makes worker state and remaining case
requirements visible in the authorized conversation.

The worker uses the deployment's existing attested subscription executor.
Its trusted client maps native cwd requests to the executor's existing mounted
workspace; host context tools keep their own confined directories. The model,
restricted dynamic tools and disabled ordinary native tools remain unchanged.
The transport identity and host bridge SHA are sealed into each native cycle.
No account directory or authentication was copied.

`cycle_limit` is a persistent project/domain-wide total across conversations
and restarts. The per-cycle producer/role/tool envelope is checked before
scheduling. A worker shutdown cancels active native tasks, joins its own bounded
daemon thread and prevents subsequent reservations; an owner pause persists
separately and is rechecked before admission/activation. Unknown interrupted
attempts retain their existing evidence and bounded recovery rules.

Automatic scheduling now seals a feedback revision, permits a new revision for
an already used DEV case, excludes promoted DEV pixels from regression, fills
small exposed regression sets and derives the exact count/call budget for a
wider prior holdout set. These repairs preserve the admission criteria.

## Private and unsupported cases

The production collector saves fixed categories, counts, opaque references and
SHAs only. It does not collect raw prompts, replies, artifact paths or provider
error text. Real cases stay unapproved and `awaiting_adapter`; a reply reference
is not permission to disclose its text. The current replay adapter supports
approved synthetic layered-media creation/repair, not arbitrary production
media/provider tasks. Monitoring these observations does not manufacture a
quality verdict or an automatic quality rollback for unsupported cases.

No learned candidate has been accepted in the recorded three cycles. The
original baseline stays active. See the
[negative quality results](../harness2-quality-cycle3-2026-10-19/README.md).

## Runtime packaging and recovery

The normal immutable release now includes the exact pinned upstream manifest,
17 locked core/license files and the new Oak bridge. Dependency bytes enter the
existing release/profile manifest. Unlisted files, changed pins, missing modules,
links and altered core bytes fail closed. Execution mounts, account paths,
identities and privileges are preserved.

The protected build manifest now covers the new host bridge and harness files.
A narrowly scoped restart repair also preserves an already acknowledged empty
reply for an exactly completed turn without replacing the existing Telegram
message with an interruption error. Sending/unknown replies retain uncertainty.

## Verification before rollout

[One real protected role smoke](protected-native-role-smoke.json) passed all ten
checks: fixed `gpt-6.1-sol / low`, actual existing CLI `0.162.1`, private profile
selection, native cwd mapping, dynamic read/view/write, response and edit SHAs.
It used one role call, eight tools and 19.262 seconds on a public synthetic
context. It started no improvement cycle and performed no Telegram/provider
actions. This tests native protocol compatibility, not media quality.

The installed gateway's code, immutable executor release, broker service paths,
current-boot attestation, authenticated feature manifest and preserved durable
queues must all be checked during rollout. A merge alone is not deployment.
Configuration and controls are described in
[the configuration guide](../../configuration.md#bounded-procedure-improvement).


The final integrated local suite ran **453 tests in 159.891 seconds**:
452 passed, one opt-in isolated nft/kernel fixture was skipped. The
[verification record](local-verification.json) binds the exact modules, changed
source bytes and original log hash. Native protocol verification above is a
separate real call. The reviewed immutable bundle contained 214 hash-verified
files, including all 18 pinned dependency files; only code_root, manifest and
policy_digest changed relative to the existing execution profile. Installation
and current-boot attestation are separate operational steps, not unit results.
