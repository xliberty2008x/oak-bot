# Control panel runtime capabilities

Oak queries its existing subscription runtime. It retains the deployment's
isolated `runtime_home`, ChatGPT authentication, and default `gpt-6.1-sol` model.
The panel must not start a second runtime, read credential files, or copy another
client's account state.

These protocol fields were checked against JSON schemas generated by local
`codex-cli 0.159.2`. Schema generation does not execute a model or verify provider
access:

```bash
codex app-server generate-json-schema --experimental --out /tmp/oak-runtime-schema
```

## Session model selection

`model/list` with `includeHidden: false`, `limit` and cursor pagination supplies
the visible model slugs, display names and default reasoning efforts. Oak uses
this catalogue for its owner-confirmed `/api/models` selection and validates it
again before saving. The selection belongs to the authenticated conversation;
General, other topics and other owners retain their own settings.

`thread/start` and `thread/resume` accept the selected `model`. `turn/start`
accepts `model` and `effort`, so changing a model preserves the existing thread
and takes effect on the next turn. `turn/steer` has no model or effort override.
The owner can choose an effort from the model's ordered
`supportedReasoningEfforts`. The server validates model/effort together; the
browser never invents additional levels. Untouched sessions display their
effective deployment default (normally `low`).
Oak rejects changes while accepted input, a scheduled run or a model turn is
being processed. Explicit choices persist through restart; untouched sessions
keep the deployment's default behavior. [Official app-server protocol](https://learn.chatgpt.com/docs/app-server)

A catalogue entry does not prove subscription entitlement. Only a completed
inference request proves that the signed-in account can use a model. Provider
errors do not trigger fallback to another model or API billing. [Official catalogue and entitlement guidance](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)

## Inventory

| Native method | Request | Relevant response |
| --- | --- | --- |
| `app/installed` | `forceRefresh`, optional loaded `threadId` | `apps`: `id`, `runtimeName`, effective `enabled`, `callable` |
| `app/read` | `appIds` (at most 100), `includeTools`, optional loaded `threadId` | `apps`: `id`, `name`, `installUrl`, `pluginDisplayNames`, `toolSummaries`; `missingAppIds` |
| `app/list` | `cursor`, `limit`, `forceRefetch`, optional `threadId` | Paginated available directory metadata; `isAccessible`, `isEnabled`, `installUrl` |
| `plugin/installed` | Optional absolute `cwds` | `marketplaces[].plugins`: `id`, `name`, `installed`, `enabled`, `authPolicy`, version and interface metadata; marketplace errors |
| `mcpServerStatus/list` | `detail: "toolsAndAuthOnly"`, optional `threadId`, `serverName`, `cursor`, `limit` | `data`: `name`, `pluginId`, `httpOrigin`, `authStatus`, `runtimeStatus`, `tools`, `toolsError`; `nextCursor` |

Use an existing thread only when it is loaded in this runtime. Omit `threadId`
otherwise and identify the result as global runtime state. Do not create or
resume a conversation just to inspect integrations.

`app/installed` reports committed runtime availability. Directory access,
installation, enablement, authentication and callable tools are separate states.
An app metadata tool summary is for display and does not authorize execution.
Keep MCP runtime status separate from stored authentication and cached tools.

MCP `authStatus` values are `unknown`, `unsupported`, `notLoggedIn`, `bearerToken`
and `oAuth`. Runtime status can be `notStarted`, `starting`, `connected`,
`authenticationRequired`, `failed`, `cancelled`, `disabled` or unavailable.
`unknown` and `unsupported` do not establish OAuth support; an anonymous server
can still be connected. Plugin `authPolicy` describes when authentication is
requested, rather than whether authentication succeeded.

Only expose selected presentation fields. Exclude credentials, raw config,
private paths, sharing/account metadata and raw provider errors. For app
management, use only a validated runtime-provided HTTPS `chatgpt.com` install URL,
without userinfo or an unexpected port. Do not invent app OAuth endpoints.

The public documentation marks `plugin/list`, `plugin/read`, installation and
uninstallation as under development. The installed-plugin route above is
present in the local schema; handle unsupported methods and partial inventory
without fabricating an empty successful result. [OpenAI app-server documentation](https://learn.chatgpt.com/docs/app-server)

## MCP OAuth

The native launch request uses the exact inventory server name:

```json
{"method":"mcpServer/oauth/login","id":1,"params":{"name":"example","timeoutSecs":300}}
```

The result contains `authorizationUrl`. Completion arrives through
`mcpServer/oauthLogin/completed` with `name`, optional `threadId`, `success` and
optional `error`. `notLoggedIn` supports offering login; stored OAuth with an
authentication-required runtime supports offering reconnect. [OpenAI app-server documentation](https://learn.chatgpt.com/docs/app-server)

Return the native URL only to the authenticated owner and keep it transient.
Do not log or persist it, rewrite its `state`/`redirect_uri`, or proxy token
exchange in Oak. Poll the native status method without configuration reloads.
If the client cannot consume completion events, show the observed auth/runtime
state and retain an unknown outcome on timeout; a launch URL alone is not success.

A loopback callback requires a browser on the runtime machine. Telegram and
remote browsers need an operator-configured reachable callback ingress using
`mcp_oauth_callback_url` plus its listener port. A URL port alone does not select
the listener. Custom callback hosts require dynamic client registration or a
pre-registered OAuth client. The ingress must preserve the callback path/query
without logging it. [OpenAI MCP documentation](https://learn.chatgpt.com/docs/extend/mcp), [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference)

Live OAuth, provider tool access, model execution and Telegram delivery require
operator verification; schema checks establish only the local protocol surface.

The implemented panel requires a valid global callback URL and fixed listener
port in Oak's `runtime_config`, plus `web.oauth_callback_ready: true` before
offering a remote OAuth launch. That flag records the operator's confirmation
that forwarding is configured; it does not prove network reachability. The
returned authorization URL must contain a redirect matching that callback,
optionally with the runtime's server-specific callback ID appended. Per-server
overrides that do not match are rejected. Direct local browser logins require
the operator's separate `web.oauth_loopback_ready: true` confirmation before
using a loopback callback. Public URLs, forwarded requests and signed Telegram
sessions do not qualify as local browsers.
